# Лабораторная работа 3. Полиморфизм и проектирование

## Как собрать и запустить

Нужны JDK 21 и Maven 3.8+; проверьте `java -version`, `javac -version`, `mvn -version`. В PowerShell из папки `lab3`:

```powershell
mvn test
mvn -q compile
java -cp target/classes coursehub.practice3.Practice3
java -cp target/classes coursehub.practice3.ExtraExamples
```

Код находится в `src/main/java/coursehub/practice3/Practice3.java`, дополнительные примеры — в `ExtraExamples.java`, тесты — в `src/test`. Типы объявлены вложенными, чтобы в одной лабораторной их было удобно читать вместе. `record` — краткая запись неизменяемого носителя данных: Java сама создаёт конструктор, методы чтения, `equals`, `hashCode`, `toString`. Maven загружает JUnit при первом запуске.

## 1. Один контракт, две реализации

`CourseFormatter` объявляет метод `String format(Course course)`. Интерфейс описывает, **что** клиент может вызвать; `CompactCourseFormatter` и `DetailedCourseFormatter` описывают, **как** выводить курс. Переменная типа `CourseFormatter` может ссылаться на любой объект, реализующий интерфейс. Компилятор проверяет, что метод существует и принимает `Course`; конкретная реализация выбирается во время выполнения по классу объекта.

## 2. Вызов и перегрузка

`AbstractNotificationSender` определяет `describe(Object)` и `describe(String)`, а `EmailSender` переопределяет первую версию. В `main` переменная `sender` имеет статический тип `AbstractNotificationSender`, объект — `EmailSender`.

| Вызов | Выбор компилятора | Фактический метод |
|---|---|---|
| `sender.describe(text)`, `text` типа Object | `describe(Object)` | `EmailSender.describe(Object)` |
| `sender.describe("hello")` | `describe(String)` | унаследованный `AbstractNotificationSender.describe(String)` |

Перегрузка выбирается по типам выражений на этапе компиляции, переопределение — по реальному объекту при выполнении. Через ссылку `NotificationSender` вызвать `describe` нельзя: метод не входит в интерфейс.

## 3. Массив интерфейсов

`CourseFormatter[]` содержит компактный, подробный и третий форматировщик `UpperCourseFormatter`. `formatAll` обходит массив и вызывает один интерфейсный метод, не спрашивая тип. Для нового форматировщика достаточно реализовать контракт и передать объект в массив; цикл не меняется.

## 4. Абстрактный класс

`AbstractNotificationSender.send` проверяет адресата и сообщение и вызывает `doSend`. Метод `send` объявлен `final`: подкласс не сможет обойти общую проверку или изменить порядок шагов. Реальную отправку задаёт `protected abstract doSend`; это точка расширения. `EmailSender` и `ConsoleSender` демонстрируют разные реализации. В примере настоящая сеть не используется, возвращается текст.

## 5. Выбор типа

| Понятие | Выбор | Обоснование и цена изменения |
|---|---|---|
| Identifiable | интерфейс | Контракт получения ID пригоден разным классам. Добавление обязательного метода затрагивает реализации. |
| CoursePolicy | интерфейс | Правила могут меняться независимо от наследования; смена контракта затрагивает клиентов и реализации. |
| BaseEntity | абстрактный класс только при реальном общем состоянии | Если всем нужен один неизменяемый ID и общий код, базовый класс устраняет повторение, но занимает единственного родителя и связывает модели. Без общего поведения лучше не вводить. |
| Formatter | интерфейс | Нужны разные алгоритмы форматирования; новая реализация не меняет клиента. |
| ClockProvider | интерфейс, когда действительно нужно подменять часы | В простом Java-приложении достаточно передавать стандартный `java.time.Clock`: отдельный тип не нужен. Дополнительная абстракция усложняет код. |

Это проектные решения, а не универсальное правило для любого приложения.

## 6. Override и случайный overload

В `ExtraExamples.Parent` метод `show(Object)`. `AccidentalOverload.show(String)` выглядит похожим, но имеет другой параметр и ничего не переопределяет. `Parent ref = new AccidentalOverload(); ref.show("x")` вызывает `Parent(Object)`: через тип `Parent` виден только этот метод. `CorrectOverride` использует идентичную сигнатуру и `@Override`, поэтому вызывается `Child(Object)`. Аннотация заставляет компилятор сообщить ошибку при несовпадении параметров. При переопределении нельзя сузить доступ; возвращаемый ссылочный тип может быть ковариантным подтипом, но не произвольным другим типом.

## 7. Композиция вместо наследования

`LoggingSender` и `MetricsSender` сами реализуют `NotificationSender` и хранят ссылку на следующий sender. Logging пишет `before/after`, metrics считает попытки и исключения. `LoggingSender(MetricsSender(email))` помещает измерение внутри логирования; `MetricsSender(LoggingSender(email))` — снаружи. Например, если сам logger выбросит исключение до вызова делегата, внешний metrics его увидит и посчитает, а внутренний metrics вообще не будет вызван. Оба декоратора можно использовать вместе с другой реализацией без наследования. Повторы можно аналогично добавить отдельным декоратором: его положение относительно metrics определит подсчёт отдельных попыток или всей операции.

## 8. LSP

Read-only репозиторий, наследующий контракт с `save`, обещает клиенту операцию, которую не выполняет. Если он всегда бросает исключение, подстановка нарушает ожидания клиента. Поэтому `CourseReader` содержит только `find`, `CourseWriter` — только `save`, а полный `CourseRepository` объединяет оба. `ReadOnlyCourses` реализует только чтение, не обещая запись.

## 9 и 15. Стратегии и движок

`Applicant` содержит признаки заявки. `EnrollmentPolicy.evaluate` возвращает `EnrollmentResult`. Пять независимых стратегий: `AgePolicy`, `PrerequisitePolicy`, `CapacityPolicy`, `PaymentPolicy`, `ActiveCoursePolicy`. `EnrollmentService` принимает любую политику конструктором и вызывает интерфейс, не проверяя классы. Добавление шестого правила не меняет сервис.

`allOf`: проверяет по порядку, возвращает первый `Rejected`; если отказов нет, но есть `WaitListed`, вернёт ожидание; иначе — `Accepted`. Пустой allOf принимает. `anyOf`: возвращает первый `Accepted`, иначе первое ожидание, иначе последний отказ; пустой anyOf отказывает. Политики вычисляются лениво до определённого результата, поэтому побочные эффекты правил нежелательны.

```text
EnrollmentService --> EnrollmentPolicy <|-- AgePolicy
                                      <|-- PrerequisitePolicy
                                      <|-- CapacityPolicy
                                      <|-- PaymentPolicy
                                      <|-- ActiveCoursePolicy
       allOf / anyOf --> список EnrollmentPolicy
EnrollmentPolicy --> sealed EnrollmentResult --> Accepted | Rejected | WaitListed
```

Стратегии открыты для расширения интерфейсом; результат закрыт `sealed`-границей, поэтому компилятор знает все допустимые варианты. Наследование уместно для общей обязательной проверки отправителей; композиция подходит для независимо комбинируемых правил и декораторов.

## 10. Default-методы

`FirstGreeting` и `SecondGreeting` предоставляют одинаковый default `greeting`. Класс `Greeting` явно переопределяет метод и выбирает `FirstGreeting.super.greeting()`. Если убрать override, компилятор сообщит конфликт default-методов. Java не выбирает поведение произвольно.

## 11. Равенство

`BadPoint.equals` принимает любой `BadPoint`, включая подкласс, а `BadColoredPoint.equals` сравнивает только цветные точки. Поэтому `plain.equals(colored)` истинно, а обратный вызов ложен: нарушена симметрия. Пример намеренно плохой; он также нарушает согласованность hashCode для такой пары. `StrictPoint` сравнивает `getClass()`, не приравнивая объекты разных классов. Второй способ — `Point` и `ColoredPoint` как отдельные `record`, где цветная точка **содержит** точку. Record final, поэтому подкласс не сможет незаметно изменить смысл равенства. Strict equality подразумевает, что подклассы корректно учитывают собственные поля в equals/hashCode.

## 12. Sealed и exhaustive switch

`EnrollmentResult` допускает только `Accepted`, `Rejected`, `WaitListed`. `describe` перечисляет все варианты в switch без `default`; требуется JDK 21. Если добавить, например, `record Deferred() implements EnrollmentResult` и включить его в `permits`, компилятор потребует новую ветку в `describe`. После эксперимента верните код обратно. Для открытого интерфейса такой гарантии полного перечисления типов нет.

## 13. Удаление кода типа

Отправка выполняется через `NotificationSender`, а не через поле `notificationType` и большой switch: отличие email/console — различный алгоритм. Выбор реализации из конфигурации всё равно можно сделать в одной фабрике. Не стоит создавать отдельный класс для каждого email-адреса или шаблона: это данные и параметры одного поведения, а не отдельные алгоритмы.

## 14. Независимые оси

`Offering` содержит `Delivery` и `Payment`. Форматы Online, Classroom, Hybrid и оплаты Free, Fixed, Subscription можно представить реализациями этих интерфейсов (перечисления `DeliveryFormat` и `PaymentPlan` реализуют соответствующие интерфейсы; SELF_PACED и INSTALLMENTS демонстрируют новые варианты). Новая доставка или оплата добавляется отдельно и не требует девяти классов комбинаций. Это выгодно, когда оси действительно независимы; особые ограничения совместимости требуют отдельной проверки.
## Как самостоятельно увидеть ошибки компилятора

Файлы в `negative` имеют расширение `.java.txt`, чтобы не ломать обычную сборку. Скопируйте каждый во временную папку под именем с расширением `.java`, затем вызовите `javac --release 21 Имя.java`. `DefaultConflict` должен сообщить о конфликте унаследованных default-методов; `Exhaustive` — о неполном switch после добавления `Later`. Исправления: явно переопределить `message` и добавить `case Later` соответственно.

Файл `negative/IncorrectOverrides.java.txt` показывает ещё три ошибки: более узкий `protected` вместо `public`, несовместимый `String` вместо `void` и другой параметр с `@Override`. Правильно оставить доступ `public`, сигнатуру параметров родителя и совместимый возвращаемый тип. Для ссылочного возвращаемого типа `Number` допустимо уточнение до `Integer`; `void` заменить на `String` нельзя.
## Разбор основных строк для защиты

В `formatAll` выражение `new ArrayList<>()` создаёт изменяемый временный список; цикл `for (CourseFormatter formatter : formatters)` последовательно получает элементы через общий интерфейс. Строка `formatter.format(c)` вызывает реализацию текущего объекта; `List.copyOf(lines)` возвращает неизменяемый снимок.

В `AbstractNotificationSender.send` проверка стоит перед вызовом `doSend`, поэтому пустой адресат не попадёт в конкретную реализацию. `final` запрещает подклассу заменить этот порядок, `abstract` у `doSend` требует предоставить реализацию. У декоратора поле `delegate` хранит следующий объект, а вызов `delegate.send(...)` передаёт ему работу. `finally` в logging выполняется и при обычном возврате, и при исключении.

В `allOf` сначала копируется список стратегий, чтобы его внешнее изменение не поменяло правило. Переменная `wait` сначала равна null. Цикл вызывает каждую политику; отказ немедленно возвращается, ожидание запоминается, а по окончании возвращается ожидание либо успех. В `anyOf` успех возвращается сразу, а отказ — только если ни одно правило не приняло и ни одно не предложило ожидание. Методы возвращают лямбду — объект, реализующий единственный метод `EnrollmentPolicy`.
