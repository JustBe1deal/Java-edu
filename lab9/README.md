# Практическая работа 9. Основы конкурентности

## Запуск

Нужны JDK 21 и Maven. Откройте PowerShell в `E:\Java-edu\lab9`:

```powershell
mvn test
java -cp target/classes coursehub.practice9.Practice9
```

`src/main/java/coursehub/practice9/Practice9.java` содержит решения, `src/test/java/coursehub/practice9/Practice9Test.java` — тесты JUnit. При разных запусках потоки могут планироваться в разном порядке, поэтому тесты не рассчитывают на паузу `Thread.sleep`. Результат обработки очереди сортируется, чтобы вывод был воспроизводимым.

## 1. Потерянные инкременты

`UnsafeCounter.increment` содержит `value++`, но эта операция не атомарна. Упрощённо она состоит из чтения старого значения, вычисления старое + 1 и записи результата. Если два потока одновременно прочитали 0 и оба записали 1, итог равен 1 вместо 2.

`forcedLostUpdate` намеренно разбивает операцию на чтение, ожидание на `CyclicBarrier` и запись. Barrier гарантирует, что оба потока прочитали исходное значение до записи, поэтому пример воспроизводит потерю обновления при каждом запуске. Это детерминированная демонстрация опасной последовательности, а не утверждение, что обычный `counter++` всегда проявляет ошибку. Тест повторяет её 20 раз.

`SynchronizedCounter` защищает методы increment и value монитором объекта `this`. `BlockCounter` использует отдельный объект `lock` и минимальные блоки synchronized. В обоих случаях **все** чтения и изменения поля выполняются под одним монитором. Инвариант: каждый успешно завершившийся increment увеличивает значение ровно на единицу, чтение видит согласованное значение. Блокировка также создаёт happens-before между освобождением и последующим захватом того же монитора. Синхронизированный метод захватывает монитор на всё тело, блок позволяет ограничить критическую секцию.

## 2. Флаг остановки и visibility

`UnsafeWorker` намеренно использует обычное поле `boolean running`. Один поток меняет флаг в stop, другой читает его в цикле run; без общей синхронизации или volatile между ними нет гарантии своевременной видимости. Факт, что пример на конкретном запуске остановился, не доказывает корректность: компилятор и процессор не обязаны обеспечивать нужный порядок видимости.

В `Worker` поле объявлено `volatile`. Запись false видима последующим чтениям этого же volatile-поля, поэтому поток покидает цикл. `CountDownLatch` сообщает тесту о запуске, `join` ограничен по времени; interrupt — дополнительная возможность остановки. `AtomicLong` в примере считает итерации. Сам volatile делает чтение и запись поля видимыми, но **не** превращает составной `count++` в атомарную операцию: два потока всё ещё могут прочитать одно старое значение.

## 3. Потокобезопасный реестр

`SessionRegistry` хранит пары id → пользователь в `ConcurrentHashMap`. `createIfAbsent` вызывает `putIfAbsent`: проверка отсутствия и вставка выполняются атомарно для одного ключа. Возвращается true только потоку, который создал запись. `remove(id, user)` удаляет соответствующую пару условно, чтобы не удалить другое значение. `null` запрещён. Тест одновременно вызывает createIfAbsent из восьми потоков и проверяет один успешный результат.

## 4. Producer–consumer и ExecutorService

`processJobs` принимает список целых заявок, число producers и consumers, размер очереди и timeout. Учебная обработка consumer удваивает каждое число с обычной арифметикой Java `int`; при переполнении действует стандартное переполнение int. Каждому исходному элементу соответствует один результат, повторы сохраняются.

1. Создаётся `ArrayBlockingQueue` ограниченной ёмкости и пул размером producers + consumers. Здесь обработчики могут блокироваться на очереди, поэтому для демонстрации каждому одновременно работающему producer и consumer отведён поток. Для реальной нагрузки размер выбирают по числу ядер, длительности блокировок и измерениям; универсального размера нет.
2. Consumers вызывают `take()` и ждут заявку без busy waiting. Producers распределяют вход по индексам и вызывают `put()`. Если очередь заполнена, producer блокируется: это **backpressure**, то есть медленный consumer ограничивает скорость поставщика.
3. После завершения всех producers вызывающий поток добавляет по одному специальному сигналу завершения каждому consumer. Поскольку сигналы помещаются после всех заявок, каждый consumer завершится только после обработки более ранних элементов.
4. Future проверяются с общим сроком ожидания; при отказе или timeout все задачи отменяются. В finally вызывается shutdown, затем ограниченное awaitTermination и при необходимости shutdownNow. Потоки называются `coursehub-queue-N`.
5. Частичные результаты consumers собираются после их завершения и сортируются; исходный список сохраняется неизменным. Блокирующие очереди и Future передают результаты между потоками с нужными гарантиями видимости.

Если один из workers перестанет отвечать, timeout ограничит ожидание; аварийное завершение зависит от того, реагирует ли выполняемый код на прерывание. В примере blocking queue реагирует на interrupt. Потокобезопасная очередь не делает произвольный пользовательский код внутри обработчика безопасным.

## 5. Детерминированный конкурентный тест

В `bothEnrollmentImplementationsPreserveInvariants` 16 задач сначала вызывают `ready.countDown()`, затем ждут `start.await()`. Тест ждёт готовности всех задач и одним `start.countDown()` разрешает им конкурировать. Для каждой Future задан ограниченный `get`, тест помечен `@Timeout`, а executor в finally останавливается через `shutdownNow` и ограниченный `awaitTermination`. Это управление точками протокола, а не задержка по времени.

В тесте счётчика `CyclicBarrier` гарантирует, что оба чтения предшествуют записям. Само наличие синхронизации в тесте не исправляет намеренно несогласованные записи счётчика: оно лишь делает сценарий воспроизводимым.

## 6. Зачисление с ограничением мест

Обе реализации предоставляют `Enrollment.enroll(student)` и снимок `students()`. Возвращаемое true означает новую успешную запись. False означает, что студент уже записан или места закончились. `null` запрещён, отрицательная ёмкость отклоняется. Отказ не меняет опубликованное состояние.

**LockedEnrollment** использует HashSet и один монитор `this`: внутри синхронизированного метода проверяются и повтор, и вместимость, затем выполняется добавление. Снимок тоже снимается под этим монитором. Код прост, но все операции конкурируют за одну блокировку — coarse-grained lock.

**ConcurrentEnrollment** хранит неизменяемый Set в `AtomicReference`. Поток получает снимок, проверяет условия, создаёт изменённую копию и пытается опубликовать её через compareAndSet. Если другой поток опередил, проверка повторяется на свежем снимке. Успешный CAS — точка атомарной публикации новой записи. Если повтор или вместимость обнаружены, изменение вообще не публикуется. Это решение без общей явной блокировки, но оно копирует весь набор при каждой попытке и при высокой конкуренции может выполнять много повторов. Выбор между подходами зависит от нагрузки; автоматического выигрыша от CAS нет.

Одна лишь `ConcurrentHashMap` или `ConcurrentHashMap.newKeySet()` защищает отдельные операции, но последовательность `size() < capacity`, затем `add()` остаётся составной и может превысить лимит. Поэтому инвариант нельзя обеспечить простой заменой HashSet на concurrent set без общей координации.

Тест запускает 16 конкурентных запросов на 8 идентификаторов при вместимости 4 для обеих реализаций. Проверяется ровно 4 успеха, размер набора 4, невозможность повторной и дополнительной записи и неизменность снимка после отказов. Отдельно проверяется нулевая вместимость.

## Разбор трудных строк

`students.add(student)` в синхронизированном варианте выполняется только после обеих проверок, пока монитор ещё удерживается. В CAS-варианте `Set.copyOf(copy)` создаёт неизменяемый снимок; `state.compareAndSet(before, ...)` публикует его, только если состояние по-прежнему является именно тем объектом, который был прочитан. Иначе while начинает попытку заново. `Set.copyOf` в результате не раскрывает изменяемый внутренний HashSet.

`queue.take()` ожидает появления элемента, а `queue.put()` — свободного места. В обоих случаях ожидание блокирующее, а не цикл постоянной проверки. `Future.get(timeout, unit)` передаёт завершённый результат или исключение задачи и не позволяет ждать неограниченно.
